## Задание 1. FastAPI + SQL-аналитика + отладка дефекта

Дан сервис на FastAPI с подключением к PostgreSQL (таблица пассажиров Titanic); один из существующих эндпойнтов возвращает некорректные данные.

Требуется:
1. Реализовать эндпойнт `GET /analytics/survival-by-class`, который возвращает долю выживших по классам обслуживания.
2. Запрос к БД оформить так, чтобы использовались группировка и агрегация, а ответ был валидирован Pydantic-моделью.
3. Воспроизвести дефект существующего эндпойнта через Swagger, локализовать источник проблемы (SQL/преобразование/модель/роутинг) и исправить его.
4. Подготовить короткий баг-репорт: шаги воспроизведения, ожидаемый/фактический результат, причина, способ проверки исправления.
5. Добавить оба сценария в Swagger и показать примеры корректных ответов.

Проверяемые модули: **M2, M3, M4, M7**.

**Форма сдачи (артефакт):**
- Ссылка на репозиторий/ветку с изменениями и `README`-инструкцией запуска.
- Файл `BUG_REPORT.md` (или раздел в отчёте) со структурой: шаги, ожидание/факт, причина, проверка фикса.
- Скриншоты/выписки из Swagger для дефектного и исправленного сценариев.

**Критерии приёмки и гайдлайн оценки:**
- `0–2` балла: эндпойнт реализован и возвращает корректную структуру ответа.
- `0–2` балла: SQL-агрегация и валидация `Pydantic` обоснованы и соответствуют задаче.
- `0–2` балла: дефект воспроизведён, локализован и исправлен без побочных поломок.
- `0–2` балла: баг-репорт полный, проверяемый, с воспроизводимыми шагами.
- `0–2` балла: Swagger-демонстрация понятна, примеры ответов консистентны данным.

Есть CSV-файл с данными Titanic.

3. Сформировать короткий EDA-профиль датасета (структура, ключевые распределения, аномальные значения) и зафиксировать 2–3 практических вывода для продуктового решения.

**Форма сдачи (артефакт):**

- Короткий текстовый вывод (`EDA_SUMMARY.md`) с 2–3 продуктовыми инсайтами.

**Критерии приёмки и гайдлайн оценки:**

- `0–2` балла: результаты воспроизводимы при повторном запуске.

## Задание 3. Проверка гипотез и согласование выводов по выживаемости

Есть CSV-файл с данными Titanic.

Требуется:
1. Сформулировать минимум 2 проверяемые гипотезы по выживаемости (например, по полу и по классу) и явно указать, какие признаки и метрики используются.

4. Сопоставить статистические результаты с визуализацией (не менее одного графика) и сформулировать итог: где выводы совпадают, а где возможна неоднозначность.
5. Явно описать ограничения выбранного критерия (допущения, чувствительность к объёму выборки) и как они влияют на интерпретацию результата.

**Форма сдачи (артефакт):**

- Краткий аналитический отчёт (`HYPOTHESIS_REPORT.md`) с выводами и ограничениями.

**Критерии приёмки и гайдлайн оценки:**
- `0–2` балла: гипотезы сформулированы проверяемо, признаки и метрики определены явно.
- `0–2` балла: preprocessing обоснован, исключения строк/полей аргументированы.

- `0–2` балла: ограничения метода описаны и связаны с практическими выводами.

## Задание 4. Сравнение пайплайнов предобработки и data-quality gate

Есть один и тот же исходный датасет Titanic для подготовки к задаче бинарной классификации и публикации аналитического API.

2. Для каждого пайплайна получить итоговый набор признаков: кодирование категорий, масштабирование числовых столбцов, контроль отсутствия пропусков.
3. Сравнить пайплайны по количественным критериям качества подготовки данных (размерность, доля удалённых записей, наличие потенциальной утечки признаков, воспроизводимость шага обработки).
4. Определить набор data-quality проверок перед публикацией (типы, диапазоны, критичные пропуски, дубликаты, согласованность категорий) и оформить их в виде проверочного шага.
5. Зафиксировать выбранный пайплайн и описать минимальный контракт интеграции для API (ожидаемые поля/типы), включая формат машиночитаемого отчёта `json/csv` со статусом готовности данных.

Проверяемые модули: **M6, M5, M7, M4, M8**.

**Форма сдачи (артефакт):**
- Скрипт/ноутбук с двумя пайплайнами и сравнительной таблицей метрик.
- Машиночитаемый отчёт data-quality (`json`/`csv`) со статусом `ready/not_ready`.
- Описание контракта интеграции (`API_CONTRACT.md`): поля, типы, обязательность, ограничения.

**Критерии приёмки и гайдлайн оценки:**

- `0–2` балла: сравнение выполнено по количественным критериям и рискам качества.
- `0–2` балла: проверки качества данных покрывают критичные сбои (типы, пропуски, дубликаты, категории).
